# 設計の狙い {#design-rationale}

`switon/context` は **可変ランタイム状態を共有サービスから出し**、所有サービスが **スコープ境界を一度だけ** 宣言できるようにします。

## 抱えていた問題 {#core-problem}

可変なサービス状態は、アプリ構造が崩れる最初の場所のひとつになりがちです。

- あるサービスがリクエストデータを自分に載せ始める
- 別ランタイムが独自の状態モデルを曝す
- 子コルーチンが状況によって状態を共有したりしなかったりする
- クリーンアップが隠れたランタイム挙動に依存する

フレームワークには **ユーザーコードで明示的** で、ランタイム横断で **予測可能** な状態境界がひとつ必要になる。

## 主な狙い {#primary-goal}

Switon Context はまず **所有者ベースのスコープ付き状態モデル** を揃え、格納のしかたはランタイムに任せる。

- **利点:** FPM・Swoole・長寿命ワーカーでサービスコードを再利用しやすい。
- **利点:** 継承した子スコープと分離した子スコープの両方で同じ API が使える。
- **代償:** 可変状態は **明示的なコンテキスト所有者契約** を通す必要がある。

## 中核の選択 {#core-choice}

サービスを所有者、コンテキストオブジェクトを可変状態の入れ物として扱う。

- `ContextAware` が所有者を示す
- `ContextManagerInterface` が現在のランタイムスコープ用のアクティブコンテキストを解決する
- `ContextIsolated` が共有が危ないとき子コルーチン境界を変える

アプリコードを複数の格納 API で教えず、**ひとつの安定した経路** に載せる。

## トレードオフ {#trade-off}

Switon Context は汎用アプリコンテナを目指さない。

- **利点:** 所有関係がはっきりする。
- **利点:** ランタイム挙動を推論しやすい。
- **代償:** 手っ取り早い一回限りの受け渡しはリクエスト属性など、より単純な境界に残る。

## 意図的な単純さ {#deliberate-simplicity}

普通のアプリ経路は小さく保つ。

- 所有者サービスは `getContext()` を呼ぶ
- 既定の子スコープはマークが無ければ状態を継承する
- 可観測性は主契約から分離する

ストレージフレームワークにせず、多くのアプリ状態に足る大きさにとどめる。
