# 設計の狙い {#design-rationale}

`switon/event` は、トランスポートや監視パイプラインと混ぜず、**プロセス内のリアクション** を小さく明示的に保つ。

## 抱えていた問題 {#core-problem}

アプリはだいたい三つのリアクション様式に散らばる:

- サービス内にインラインの副作用
- 別のリスナーフック
- 非同期トランスポートへ押し出し

Switon event は、キュー・RPC・ワークフローの前に **ひとつの明確なプロセス内境界** を置く。

## 標準化するもの {#what-it-standardizes}

- identity とペイロード用のクラスベースイベント
- ハンドラ近くの `#[EventListener]` 登録
- 現在プロセス内の同期 dispatch
- 横断観測用の `object` リスナー
- ログ・トレース・メトリクス用の `ObservabilityProbe`
- 意図的停止の `StopFlow`
- 別パイプラインなしの自動ログ `EventLogger`
- 登録イベントと dispatch ごとの可観測カウントは診断用（第二のルーティング層ではない）

## トレードオフ {#trade-offs}

よくある経路は単純に保つが、キュー・トランスポート・リトライシステムにはしない。

- **利点:** イベントフローが読みやすくデバッグしやすい。
- **利点:** クラスベースマッチでルーティングが明示的。
- **代償:** 非同期配信とリトライ方針はパッケージ外。
- **代償:** 可観測性と業務リアクションの小さな区別が要る。
