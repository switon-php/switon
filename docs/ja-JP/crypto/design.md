# 設計の狙い {#design-rationale}

`switon/crypto` は可逆暗号を **小さく・決定的に・ローテーションしやすく** 保つ。

## 抱えていた問題 {#core-problem}

暗号まわりは、アプリごとにキーの意味・検証ルール・移行経路を発明しがちです。

- あるサービスは呼び出し文字列を秘密として扱う
- 別のは業務コンテキストからキーを派生する
- また別のはデプロイ後も旧暗号文を読みたい
- 検証ルールが守るべきデータ形からずれる

フレームワークには、ユーザーコードで予測可能で運用しやすい **ひとつの可逆暗号境界** が要る。

## 主な狙い {#primary-goal}

まず `encrypt()` / `decrypt()` の契約を揃え、その上に決定的派生・検証・ローテーションを載せる。

- アプリコードは安定した暗号の形を保つ
- 派生キーは保存やルックアップで再現可能
- 構造化プレーンテキストは受け入れ前に検査できる
- 移行期間でも呼び出し側を全部書き換えなくてよい

## 中核の選択 {#core-choice}

各暗号呼び出しは自己完結の操作として扱う。

- `mode` が入力キーの解釈を決める
- `ValidatorInterface` が復号と受け入れの間に入る
- `RotatingCipher` はハンドラツリーではなく二つの cipher を合成する
- `getDerivedKey()` は安定素材を要る他コンポーネント向け

呼び出し側をルーティング内部に晒さず説明しやすくする。

## トレードオフ {#trade-off}

最大のルーティング柔軟性より **予測可能性** を優先する。

- **利点:** 失敗の理由付けがしやすい。
- **利点:** 移行ロジックが明示的。
- **代償:** 汎用 KMS や公開鍵ワークフローは対象外。
- **代償:** 宛先ごとのハンドラツリーは範囲外。

## 意図的な単純さ {#deliberate-simplicity}

公開契約は意図的に狭い。

- 派生出力は小文字 hex
- 検証ルールは小さく明示的
- キー生成は `Switon\Crypto\Command\KeyCommand` に置く
- レガシーフォールバックは同じ検証ルールを再適用しない

可逆暗号・移行・運用者向けキー生成をひとつの塊に潰さないための分離。
