# 設計の狙い {#design-rationale}

`switon/console` は **ターミナル特有の仕組み** を core からもコマンドの本文からも外に出します。

## 抱えていた問題 {#core-problem}

ターミナル出力では次の三つが一緒に書かれがちです。

- その場更新の進捗描画
- 端末幅の取得
- ANSI スタイルフラグ

アプリがコマンド内でそれぞれを再実装すると、だいたいうるさくてバラつく。

## 主な狙い {#primary-goal}

フルターミナルフレームワークではなく、**小さな再利用原語** を出す。

- **利点:** アプリは進捗モデルと幅モデルを共有できる。
- **利点:** CLI コマンド・ワーカー・コンソールへ書き出すほかのコードからも使える。
- **代償:** 統合は明示的。このパッケージはバインディングやアプリポリシーを決めない。

## なぜ分けたか {#separate-pieces}

`ProgressBar`、`TerminalWidthDetector`、`Colors` は別問題なので、それぞれ単純なまま独立させる。

- `ProgressBar` — その場進捗の状態と描画ヒント
- `TerminalWidthDetector` — 幅の取得とキャッシュ
- `Colors` — `Switon\Core\ConsoleInterface::colorize()` 向け ANSI ビットマスク

分離すると直接使いやすく、既に自前ターミナル層があるアプリでは差し替えもしやすい。

## トレードオフ {#trade-off}

`switon/console` はアプリのバインディングやコマンド UX を単独では登録しない。

- **利点:** パッケージは邪魔にならず再利用しやすい。
- **利点:** `switon/cli` がコマンド面を持ち、原語を二重にしない。
- **代償:** コンテナでインターフェースの配線をアプリが決める。

## 意図的な単純さ {#deliberate-simplicity}

大きな機能集合より **安定したターミナル挙動** を優先する。

- 進捗は必要なら自動で始まり、きれいに改行で終わる
- 幅検出は最初に使える結果をキャッシュ
- 色は別テーマシステムではなくビットマスクのまま

ターミナル UI ツールキットにはならないが、よくある出力経路には十分。
