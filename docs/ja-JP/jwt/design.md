# 設計の狙い {#design-rationale}

`switon/jwt` は汎用 JWT プラットフォームに広がらず、アプリ所有 HMAC トークン向けに **ひとつの厳格なトークン境界** を保つ。

## 抱えていた問題 {#core-problem}

トークン処理は、一部だけ検証する経路と、早すぎる時点でクレームを信頼する経路が混ざるとすぐ乱れる。

## 主目的 {#primary-goal}

アプリ発行トークン向けに **検証済みクレーム境界をひとつ** に:

- **利点:** 呼び出し側は信頼できるクレーム結果と型付き失敗を得る
- **利点:** トークンデータが信頼入力になるのは `decode()` のみ
- **代償:** 公開鍵フェデレーションや広い JWT プラットフォーム機能はパッケージ外

## 中核の選択 {#core-choices}

- **HMAC のみ:** よくあるアプリ所有トークンを `HS256`・`HS384`・`HS512` でカバー
- **境界ひとつ:** `decode()` が構造・ヘッダ・署名・時間を検証してからクレームを返す
- **トークンファミリルーティング:** キールーティングをトークン境界で明示
- **型付き失敗:** 不正・署名・期限・not-before・アルゴリズム・kid 不一致を分離

## トレードオフ {#trade-offs}

- 呼び出し API は小さいが部分検証経路はない
- キールーティングは明示的だがファミリ選択は呼び出し側の責任
- クレームは消費しやすいがリフレッシュトークンや広い認証システムは別
