# 設計の狙い {#design-rationale}

`switon/http` はランタイム固有の詳細を出す前に、**アプリケーション HTTP 境界** をひとつに標準化する。

## 参照 {#see-also}

- [HTTP パッケージ](README.md) — 主ガイドと設定
- [FAQ](faq.md) — よくある質問

---

## 抱えていた問題 {#core-problem}

ルーティング・入力・レスポンス・横断フックをアプリごとに決めると HTTP 構造はすぐ漂流する:

- コントローラにトランスポート解析と業務が混ざる
- リクエスト全体の関心の実装様式がばらける
- ランタイム前提が通常のアプリコードに漏れる

## 主目的 {#primary-goal}

アプリとランタイムで主な HTTP 形状を安定させる:

- **利点:** コントローラアクションが読みやすくコピーしやすい
- **利点:** リクエスト横断の挙動が集中する
- **代償:** 一部の低レベルランタイム技巧は既定経路の外

## この形状の理由 {#why-this-shape}

- コントローラ — ルート宣言とアクション入口
- `RequestInterface` — 読み取り
- `ResponseInterface` — 書き込み
- ライフサイクルイベント — リクエスト横断フック
- `ServerOptions` — ランタイム選択

大きな内部モデルに押し込まず、フレームワーク境界を見えるままにする。

## 型付き入力とレスポンス境界 {#typed-input-and-response-boundaries}

型付き入力クラスでアクションから繰り返しパースを外す。

- `#[RequestBody]` — ボディを明示
- `#[RequestQuery]` — クエリを明示
- `#[RequestData]` — マージ入力を明示

レスポンス整形は分離し、JSON のよくある経路は配列返却、`ResponseInterface` は HTTP 形状が本当に要るときだけ。
