# 設計の狙い {#design-rationale}

Switon DB が生 SQL を明示的な境界に置く理由 — アプリごとにスタイルを発明させない。

## 既定はステートレス {#stateless-by-default}

共有の `Switon\Db\ClientInterface` は呼び出しごとに接続を借りる。通常の読み書きは単純で、プールと相性がよく、サービス内にトランザクション状態を隠さない。

読み書きルーティングを可能にしつつ、すべてのサービスを接続所有者にしない。

## ローカルスコープの明示的ピン {#explicit-local-scopes}

トランザクションと書き込み直後の読み取りは、ひとつのローカルスコープでひとつの接続が要る。`getTransient('default')` がその境界を明示する。

共有クライアントは便利に見えるが、ピンが隠れるとステートレス呼び出しと接続束縛作業が混ざりやすい。

## ORM トランザクションスコープの分離 {#separate-transaction-scopes}

`Switon\Db\TransactionManagerInterface` は ORM 主導スコープ用。生 SQL がすでにバインドされたクライアントに参加するとき、そのクライアントを返し、後から推測しない。

ORM 調整と直接 SQL は契約を分けつつ、トランザクション境界で合流できる。

## 安全な書き込みと可搬 SQL {#safe-portable-sql}

空の書き込み条件は早期失敗。`[identifier]` で手書き SQL をサポートドライバ間で可搬に保つ。

広い更新をコード上で意図的に見せ、クォートが特定ドライバ寄りに漂わないようにする。

## URI 駆動ルーティング {#uri-driven-routing}

URI がひとつならトポロジもひとつ。複数 URI なら先頭がマスター、残りがレプリカ。

カスタムルーティング DSL より小さく、よくある形（単一 DB、ピン留めトランザクション、マスター+レプリカ）をカバーする。

## ラッパーよりイベント {#events-over-wrappers}

DB ライフサイクルイベントでクエリとトランザクションを監視し、業務サービスにトレースコードを押し込まない。

メトリクスやデバッグには `SqlCollector` などのリスナー／コレクタを使う。
