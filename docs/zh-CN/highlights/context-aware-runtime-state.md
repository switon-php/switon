# 上下文感知的运行时状态 {#context-aware-runtime-state}

`Switon\Core\ContextAware` 与 `Switon\Core\ContextManagerInterface` 是 Switon 的核心框架判断之一：可变运行时状态应显式、类型化，并作用域于当前逻辑请求或协程，而非活在共享服务实例上。

**为何是亮点：**
- **清晰的状态边界** — 可变运行时状态位于专用的 `*Context` 对象，而非单例服务属性
- **容器保持专注** — DI 容器仍解析服务；它不会变成通用请求袋
- **运行时安全的默认** — 同一服务代码在 FPM、Swoole 与长生命周期 worker 进程中保持安全
- **可复用的业务服务** — 应用逻辑保持一个服务 API，运行时状态存储分离

## Switon 的决策 {#decision-makes}

Switon 将状态生命周期视为框架边界。

若数据属于一个逻辑请求或协程，且一个长生命周期服务需要在多个方法间变更它，该服务应实现 `Switon\Core\ContextAware`，并将存储委托给 `Switon\Core\ContextManagerInterface`。

这避免两种常见失败模式：

- 把请求局部可变数据放在共享服务属性上
- 把容器或请求对象变成万能状态传输

## 为何优于请求袋 {#beats-request-bag}

请求袋容易被过度使用。一旦每个服务都能向共享袋推入任意可变值，归属变得不清，类型边界消失。

Switon 保持更窄的边界：

- 服务通过其 `*Context` 类拥有状态形态
- 运行时通过 `ContextManagerInterface` 拥有作用域解析
- 容器仍拥有依赖解析

这在不瓦解服务边界的情况下提供请求局部可变性。

## 为何跨运行时仍安全 {#safe-across-runtimes}

在 FPM 下，不安全的可变服务属性可能看起来无害，因为进程生命周期短。
在 Swoole 或 worker 式运行时，同一共享服务实例可跨许多逻辑请求存活。

Switon 标准化安全路径：

- 共享服务在实例属性层面保持实质上无状态
- 可变运行时状态移入按运行时作用域解析的上下文对象
- 业务代码无论运行时模型如何，仍调用同一服务方法

因此该模式从 FPM 扩展到协程与 worker 运行时，而无需改变面向应用的服务设计。

## 何时使用 {#use-it}

当以下全部为真时使用该模型：

- 状态是可变的
- 状态仅属于当前逻辑请求或协程
- 一个服务需要在多次方法调用间持有该状态

不要用于无状态服务。
不要用于跨请求的持久数据，如数据库记录或 session 支持的持久化。
对于简单的仅 HTTP 传递值，请求属性可能仍是更小的工具。
