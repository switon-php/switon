# 理解 Switon 框架方法论 {#framework-methodology}

想先用最短篇幅弄清楚 Switon 想在各应用之间统一什么、又刻意把什么留给应用，就读这一页。

Switon 不是靠更大的抽象把更多行为藏起来取胜。它要做的是，在**不拿走本该留在应用里的业务所有权**的前提下，让应用代码里那些分散的使用边界变得一致。

## 一句话版 {#one-sentence-version}

Switon 想让重复的使用边界在各应用里看起来一致；业务所有权、存储形态和产品策略，只有在框架能干净地标准化时才会被接管，否则仍然属于应用。

## 实践里意味着什么 {#means-practice}

Switon 通常先让这些位置收敛：

- controller 与 action 边界
- 请求入参与校验边界
- 渲染与响应边界
- command、worker、定时任务边界
- 其他如果不统一就会在项目间漂移的入口侧使用模式

这些位置是开发者最常复制、最常评审、也最常让 AI 生成的地方。边界一旦收敛，即使业务模型不同，应用看起来也会像同一套框架下的产物。

## Switon 通常不试图拥有什么 {#try-own}

当框架无法干净地标准化时，Switon 不会强行指定一种应用专属的存储模型、业务策略模型或领域结构。

通常意味着：

- 业务所有权留在应用
- 在框架能给出清晰默认边界之前，策略选择也留在应用
- 存储形态留在应用，除非某个组件能在不变成隐藏应用模板的前提下把它标准化

这也是许多 Switon 组件花大量篇幅讲边界的原因：框架是在减少使用漂移，而不是接管每一个实现选择。

## 对包设计的意义 {#design}

这套方法论可以解释一些常见的包级决策：

- 某个包标准化用法，但不强迫一种存储模型
- 某个包提供传输或执行原语，把投递策略留给应用
- 某个包把公共契约保持得小而精，把业务相关的组合留到外侧

所以读 Switon 的 `design.md` 时，关键问题不只是“它怎么工作”，还有“它想让哪一种分散的应用问题变得更一致？”

## 对文档的意义 {#docs}

Switon 文档也遵循同一套方法论。

- `README.md` 帮你采用包边界
- `faq.md` 帮你在这个边界上卡住时恢复
- `design.md` 解释框架为什么需要那条边界

这三份文件只是可见结果。更深的目标是帮读者：

- 选对边界
- 快速解阻
- 理解框架的标准化逻辑
