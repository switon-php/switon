# 设计说明 {#design-rationale}

`switon/command` 把**命令发现**与**元数据**放在同一层，这样 CLI 帮助与 AI 工具读到的始终是同一种形状。

## 参见 {#see-also}

- [Command 包](README.md#command-package) —— 用法、元数据与对外契约
- [FAQ](faq.md#command-faq) —— 常见问题

## 要解决的问题 {#core-problem}

命令相关逻辑容易往三个方向**分叉**：

- 各消费者自己发明一套发现规则；
- 有人从零拼帮助文案；
- 再单独维护一套 AI / 工具注解。

Switon 把这些压进**同一套元数据模型**，作者只描述一次命令本身。

## 首要目标 {#primary-goal}

在成为「执行器」之前，先统一命令名、可见性、摘要与别名语义。

- **好处：** CLI 与 Beacon 共用同一份命令定义；
- **好处：** 帮助与工具元数据不易各写各的；
- **代价：** 执行、调度、传输不在本包。

## 核心选型 {#core-choice}

类名定一族命令，`*Action()` 定入口，属性叠加行为说明。

- 发现阶段建「名字注册表」；
- 巡检阶段读摘要、动作、参数；
- `#[Hidden]`、`#[Tool]`、`#[ShortOption]` 都**小而局部**，贴在声明上。

模型保持可扫读，而不会膨胀成完整「命令框架」。

## 取舍 {#trade-off}

本包**不**承担调用编排、Shell 交互体验或预生成命令目录。

- **好处：** 元数据层可被多终端复用；
- **好处：** 同一类既能喂给 CLI 帮助，也能喂给 AI 工具；
- **代价：** 更上层的行为仍在 CLI 等相关包。

## 刻意保持简单 {#deliberate-simplicity}

包在**稳定的作者接口**处停住：

- 发现返回缓存映射；
- 动作信息来自反射与 PHPDoc；
- `#[Tool]` 刻意限制为短文；
- 隐藏项仍可运行。

这覆盖常见「写命令」路径，又不要求本包吞下整个运维体验。
